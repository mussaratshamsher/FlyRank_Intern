# Week 06 — Connect to an Existing API

## Assignment objective

The task for Week 06 is to **connect to an existing API** via HTTP. Instead of
building a new API from scratch, I reused the minimal FastAPI service from
Week 01 and wrote a Python client that sends real HTTP requests to it, parses
the responses, and handles errors gracefully. I also added an optional
Groq-powered dynamic endpoint that generates AI terms on-the-fly using an LLM.

## Which existing API was reused

**Week-01/API_endpoint/api/** — a tiny FastAPI application that serves AI
terminology data from a hardcoded list.

## What the API does

The API exposes three `GET` endpoints:

| Endpoint            | Source        | Description                                           |
|---------------------|---------------|-------------------------------------------------------|
| `GET /`             | Original      | Returns a welcome message and list of endpoints.      |
| `GET /term`         | Original      | Returns a random AI term from a hardcoded list.       |
| `GET /term/dynamic` | New (Groq)    | Returns a random AI term generated by a Groq LLM.     |

The original endpoints are preserved unchanged. No databases, queues, or
authentication are introduced.

## API endpoints

### `GET /`

**Request:** `GET http://localhost:8000/`

**Response (200):**
```json
{
  "message": "Welcome! This is a minimal FastAPI REST API.",
  "endpoints": [
    {"method": "GET", "path": "/"},
    {"method": "GET", "path": "/term"},
    {"method": "GET", "path": "/term/dynamic"}
  ]
}
```

### `GET /term`

**Request:** `GET http://localhost:8000/term`

**Response (200):**
```json
{
  "term": "Embedding",
  "definition": "Embeddings are vector representations that capture meaning so similar text can be found efficiently."
}
```

### `GET /term/dynamic`

**Request:** `GET http://localhost:8000/term/dynamic`

Requires `GROQ_API_KEY` in the environment.

**Response (200):**
```json
{
  "term": "Neural Network",
  "definition": "A neural network is a computing system inspired by the human brain that learns patterns from data."
}
```

**Response (503 — Groq key not set):**
```json
{"detail": "Groq API key not configured. Set GROQ_API_KEY in your environment or .env file."}
```

## Request format

- `GET /` — no body, no query params.
- `GET /term` — no body, no query params.
- `GET /term/dynamic` — no body, no query params. All config comes from the
  `GROQ_API_KEY` environment variable.

## Response format

All successful responses are JSON with a `200` status code. Errors return the
appropriate HTTP status code (`404` for unknown paths, `503` for missing Groq
key, `500` for internal server errors).

## How the client connects to the API

The client (`client/api_client.py`) uses the standard `requests` library. It
does **not** import any internal Python functions from the API module — every
interaction is a real HTTP round-trip using `requests.get()`.

Key design:

1. **`AIClient` class** — holds `base_url` and `timeout`, exposes
   `health_check()`, `get_random_term()`, and `get_dynamic_term()`.
2. **`_get()` helper** — performs `requests.get(...)`, catches
   `requests.ConnectionError` → raises `APIConnectionError`, and checks for
   non-200 status → raises `APIError` with the status code.
3. **`APIError` / `APIConnectionError`** — custom exceptions that let callers
   branch on error type (server error vs. connection failure).

## Request → API → response flow

```
┌──────────────┐  HTTP GET /term/dynamic  ┌──────────────────┐
│   Client     │ ───────────────────────→ │   FastAPI server  │
│ (requests)   │                         │   (api/index.py)  │
│              │                         │       ├── Groq   │
└──────────────┘ ◄────────────────────── └──────────────────┘
                   JSON: {"term": "...", "definition": "..."}
┌──────────────┐
│  Print / use  │
└──────────────┘
```

## Installation / setup

```bash
cd Week-06/03-connect-api
python -m venv venv
venv\Scripts\activate      # Windows
source venv/bin/activate   # Linux / macOS
pip install -r requirements.txt
```

Create a `.env` file (see below) with your Groq API key if you want to use the
dynamic endpoint:

```bash
cp .env.example .env
# Edit .env and paste your Groq API key
```

## How to start the API

```bash
cd Week-06/03-connect-api
python -m uvicorn api.index:app --reload
```

The server will be available at `http://localhost:8000`.

## How to run the client

```bash
cd Week-06/03-connect-api
python -m client.demo
# or:
python client/demo.py
```

The demo prints the server's welcome message, a random cached AI term, and a
dynamically generated AI term (via Groq).

## Example request

```bash
# Static term
```

```json
{
```

## Error handling

| Scenario                | Behaviour                                              |
|-------------------------|--------------------------------------------------------|
| Server not running      | `APIConnectionError` raised → printed, exit code 1     |
| HTTP 4xx / 5xx          | `APIError` raised with status code and body text      |
| Invalid JSON            | `requests.JSONDecodeError` (standard `requests` error) |
| Missing `GROQ_API_KEY`  | API returns 503 with a descriptive `"detail"` message  |

## What I learned

- Connecting to an existing API is primarily about understanding the endpoint
  contract (paths, methods, request/response shapes) and writing a thin HTTP
  wrapper around it.
- Using the `requests` library keeps the client extremely readable.
- Proper error handling (connection errors, non-200 responses) makes the
  client robust without adding complexity.
- Adding a Groq LLM endpoint is straightforward with the `groq` Python SDK,
  and keeping it as an optional separate endpoint preserves the original API.
- Starting the server and client as separate processes clearly separates
  the server and consumer responsibilities.
